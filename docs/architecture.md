# Architecture

The daemon owns projects, workspaces, agents, relationships and completion delivery. This plugin adds a form, a task-list projection, and a project-discovery tool. It does not introduce a second execution engine or task database.

`index.server.ts` registers RPCs and a session-open hook. Only coordinators carrying the plugin label receive the discovery tool. Its unique name avoids a collision if Paseo later ships the upstream `list_projects` proposal. The hook runs on every session open, including resume; no tool implementation is stored inside agent persistence.

The form snapshots the selected project IDs, roots and kinds. Launch validates those against the current registry before creating a coordinator. The coordinator validates again when dispatching. Names and paths are prompt data; the fixed instructions precede the user's task.

The stock SDK's provider/config APIs supply preflight information. There is no dependency on the fork-only `paseoTools` feature response field. The daemon remains responsible for enforcing actual provider tool policy and transport support. A provider that cannot open the contributed tools fails through normal Paseo error handling.

Paseo stores one configuration per provider in the plugin's host settings document. Selecting a provider copies the saved configuration into the task form. Reset reloads that provider's saved choices into the draft. Launch sends the effective draft config to the coordinator and worker instructions, and settings updates leave an open draft and its launch retry unchanged.

The defaults editor loads the provider catalog and fetches projects only when the user chooses a project context. Both forms use the full draft config for feature discovery so providers can expose dependent options. Settings use the chosen project or the daemon home directory, and a task uses its first project. If a provider rejects the draft, the forms query its controls without overrides and reapply advertised values in batches so valid parent values can reveal dependent options. The forms flag unavailable values for selective removal. A deliberate option edit drops previously valid values that the provider hides in the same context. Settings writes use Paseo's revision checks. Retrying a conflicted save reads the latest document and replaces only the edited provider entry against that revision. After a conflicted removal, the user can reload the latest values and retry.

Coordinator context uses a normal Local directory workspace. The selected isolation applies to workers. Context and agent creation have separate daemon idempotency keys derived from a prepared run ID. A lost RPC response can therefore be retried unchanged within the form's lifetime. The keys live in daemon persistence, not plugin process memory. A public creation progress snapshot must explicitly report an agent-stage failure with `outcomeUnknown: false` and no registered agent before failed-launch cleanup runs. It reuses the Local workspace guards below and also excludes workspaces containing archived agents. A structured launch failure tells the form to discard that attempt identity; the next submit prepares a new one. This also handles a lost failure response: replaying the old identity may return an archived context workspace, whose rejected agent creation produces another definite failure and the same reset instruction. Missing progress or uncertain outcomes preserve both workspace and identity.

The coordinator dispatches through stock `create_workspace` and agent-scoped `create_agent` with finish notifications enabled. It yields after dispatch. Paseo may batch concurrent notifications into one provider prompt; each child still contributes its own notification envelope. Tests assert envelopes and child IDs, not a prompt count.

The client borrows the host's plugin SDK connection. The initial task read starts after agent subscription setup has completed or failed, so the first snapshot needs no separate invalidation and a failed observation still allows task loading. Later snapshots and directory updates coalesce with a 750 ms trailing debounce and a maximum wait of two seconds during sustained activity. Cleanup releases the observation and cancels both timers. Task listing follows pagination and derives workers from the persisted parent label. It also recognizes fork-created task coordinators, without adapting their old prompts or tools.

Task archival uses agent APIs. The plugin owns the confirmation because the supported stock API exposes only an after-archive hook. Keep workers detaches direct children while preserving their own subagent trees; worker cleanup includes descendants across workspaces. A worker failure leaves the coordinator available for retry.

Optional workspace cleanup is off by default and runs only after task archival succeeds. Candidate workspace IDs come from the coordinator and, when workers are archived, its descendant agent records captured before archival. Each candidate must be a Local directory workspace with explicit non-managed checkout ownership, no running setup/services, no terminals and no remaining active agents, including background/internal agents. Agent checks follow pagination and are refreshed immediately before workspace archival. Workspace archival can remove managed checkouts, so managed or unverified workspaces are skipped. The public API has no conditional archive operation; another client creating an agent between the final check and archival remains a race. Cleanup failures are returned separately and displayed on the screen after the task card disappears.

The supported SDK exposes agent attachment submission but no public plugin upload store or native file picker. The plugin therefore owns durable attachment copies; [Data and scope](../README.md#data-and-scope) owns their location and retention. Upload references keep file bytes out of coordinator labels and retry identities. Launch verifies the stored bytes before creating a workspace. Common image formats also use the coordinator's public image-input API. Worker dispatch stays on the stock `create_agent` tool so finish notifications retain their daemon ownership; that tool accepts text, so the coordinator passes shared attachment paths rather than embedding image bytes there. A worker's parent label also grants a task-scoped attachment lookup tool on every session open, so access does not depend on the coordinator copying the list correctly.

The production import graph contains only public plugin/SDK types and host runtime modules. Stock-package test utilities and the real Codex adapter are pinned development-only fixtures; users do not install those dependencies to run the plugin.
